# HC32F460 整机发布与 SWD 烧录

操作员领取一个整机镜像 `ntn-ota-l0.hex`。该文件含 BL1、按 112 KiB 补齐的 BL2，以及带签名、已确认的完整 App 主槽。工位程序和 Keil 下载工程可以随发布工具发放。开发样板使用 L0 配方。设置量产读写保护、写片外 NOR 的工厂恢复副本属于另外的工序。

## ABI 2 开发板迁移与复测

首次从 ABI 1 迁移到 ABI 2 时，用 L0 工位的 ALL 镜像同步更新 BL1、BL2、App；如果板上装有片外 factory，同步更新它并回读校验。迁移后网页接收同代 App。旧版设备可以继续配套旧发布包。本项目的网页串口传输只更新 App，无法改变 BL1 的 ICG 或 BL2 的兼容策略。

本代发布时只签一次 App。网页从整机 HEX 提取的紧凑镜像、`app.signed.bin`、`factory.signed.bin` 应逐字节相同。`app.confirmed.bin` 在同一紧凑镜像后补齐主槽并设置 MCUboot 确认标志。签名私钥保存在受控签名环境，BL2 内含验签公钥，工位使用批准发布物。L1 调试保护凭据单独管理。

NOR 初始化失败时，BL2 独立检查片内主槽的确认状态和签名。通过后在 PC 串口报告 `BOOT2 WARN NOR_INIT_FALLBACK_PRIMARY`，启动业务 App，保留现有升级记录。主槽未确认、不完整或验签失败时报告 `BOOT2 ERROR NOR_INIT`，保留故障供诊断。App 启动后可用 `AT+MCUSELFTEST?` 查询 NOR 和离线存储状态。升级暂存和断点恢复仍需可用的 NOR。正常 NOR 配合损坏主槽时可走 RS232 恢复。量产需独立验证 factory 写入、断电恢复和保护配置。

## 发布人员

在 HC32F460 BSP 根目录运行。先完成 App 的 Keil 编译。修改 BL2 时先编译 BL2，运行 `python boot/package_image.py extract-bl2`，再用 `python boot/prepare_mdk.py --bl2-bin build/ntn-ota/bl2.bin --watchdog` 重新生成并编译 BL1。版本号和密钥路径按实际发布配置填写。

```powershell
# 仅生成紧凑网页包 app.signed.bin
python boot/package_image.py sign --version 1.0.2 --key build/ntn-ota/dev-private.pem --public-key build/ntn-ota/dev-public.pem

# 生成三段整机 HEX、Keil 下载工程、分区 HEX 和工位脚本
python boot/package_image.py provision --version 1.0.2 --key build/ntn-ota/dev-private.pem --public-key build/ntn-ota/dev-public.pem
Get-FileHash build/ntn-ota/ntn-ota-l0.hex -Algorithm SHA256
```

把本次发布的 SHA-256 记入工单。每次重新签名均重新记录。装机工位只领取发布产物和工具，私钥留在签名环境。工位建议在干净目录中部署，避免复制包含开发密钥的整个构建目录。

## Keil 的 Download 按钮

在 `build/ntn-ota` 打开 `flash.uvprojx`。在 Target 下拉框选目标，然后点击 **Flash → Download**。这个工程直接使用发布好的 HEX，打开后即可下载。机器需安装 Python、`intelhex` 和 SEGGER J-Link Commander，配置好 J-Link 的 SWD 连接。下载工程通过外部工具启动 J-Link，逐段独立回读。

| Target | 对应文件 | 片内范围与用途 |
| --- | --- | --- |
| ALL | `ntn-ota-l0.hex` | 一次写 BL1、BL2、签名 App，工厂首装选此项 |
| BL1 | `flash-bl1.hex` | 从 `0x00000000` 写入，含 ICG，需与板上 BL2 配套 |
| BL2 | `flash-bl2.hex` | `0x00004000–0x0001FFFF`，包含参与摘要的尾部填充 |
| APP | `flash-primary.hex` | `0x00020000–0x0007DFFF`，包含镜像头、签名、确认标记 |

每次以同目录 `download-目标.log` 的本次时间戳及末行 `PASS 文件名 SHA256=...` 验收。App 业务工程的 Download 会烧裸 AXF；直接装签名业务固件应选此处的 APP。更改 BL2 后一起更新其对应的 BL1，整机选择 ALL 即可。

换机部署 Keil 工位时，带上 `flash.uvprojx`、`flash.uvoptx`、`download-*.cmd`、`flash_station.py` 和要使用的目标 HEX。路径保持在同一目录。每个目标的启动脚本已绑定该次发布的镜像哈希。多探针工位使用下方显式指定探针的命令。

## J-Link 工位与批量生产

工位只需安装一次 SEGGER J-Link 和 Python 的 `intelhex` 包。以下命令在工位产物目录执行。将 `$releaseHash` 设为工单给出的 64 位 SHA-256。默认在 Windows 的 SEGGER 安装目录寻找 Commander，也可用 `--jlink` 或环境变量 `JLINK_EXE` 指定。连接 SWD，选择芯片 HC32F460xE，速度 1000 kHz。

```powershell
$releaseHash = '替换为工单上的整机HEX哈希'
python flash_station.py ntn-ota-l0.hex --sha256 $releaseHash --probe 603000869
```

多工位在同一台电脑上每个夹具接一个 J-Link。每批扫码建立 `fixtures.csv`，`unit` 填本台产品编号，`probe` 填该位置的真实探针序列号。一次命令并行执行整批，每台板写一次整机镜像。

```csv
unit,probe
NTN0001,603000869
NTN0002,123456789
```

```powershell
python flash_batch.py ntn-ota-l0.hex fixtures.csv --sha256 $releaseHash
```

脚本拒绝重复板号、重复探针或错误的发布哈希。每个工位单独建立烧录会话，回读并比对镜像覆盖的每个地址段。批次日志放在当前目录新建的 `flash-log-*` 中。任一工位失败时，批命令返回非零。保留日志并只把失败板列入重试清单。单板冷启动和串口 `AT+MCUOTASTAT?` 属于功能验收，独立于 SWD 字节回读。

## PC 网页使用同一整机文件

打开网页仓库 `boot` 分支的本地服务，桌面 Chrome/Edge 连接设备。样机为 COM9、19200、8N1。进入 **MCU 固件升级**，选择同一份 `ntn-ota-l0.hex`，点击 **升级 MCU**。已有 `app.signed.bin` 也可直接选择。页面核对 HEX 记录和地址，提取 App 签名镜像，核对 Boot 报告的 ABI、布局与接收上限后进行 YMODEM 传输。设备使用自身公钥验签、试运行并确认。以页面 **已确认固件** 和目标构建 ID 为准。

网页路径要求板上已有可工作的 BL1 和兼容的 BL2。Web Serial 仅传输包内的 App，设备上两个 Boot 的字节及公钥通过 SWD 配套更新；ABI 相同不代表 Boot 字节相同。若产品要求已封装设备通过 RS232 替换 BL2，需要更改 BL1 的授权与可恢复更新设计。要求远程覆盖 BL1 本身则与现有出厂锁写方案冲突。
